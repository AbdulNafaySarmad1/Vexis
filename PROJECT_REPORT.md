# Building an x86-64 disassembler and CFG engine from scratch

## 1. The core idea

I built a x86-64 instruction decoder, disassembler, and control-flow-graph engine in Rust, entirely from scratch. No Capstone, no Zydis, no `iced-x86` in the actual decode path. If you strip a binary's headers away you're left with a stream of raw bytes, and turning that stream back into "this is a `mov`, this is a `call`, this instruction branches to that address" is a real, non-trivial parsing problem with its own grammar (variable-length instructions, prefix bytes that change the meaning of everything after them, addressing modes that can reference a register, a memory location computed from up to two registers and a scale factor, or an address relative to the instruction pointer). I wanted to prove I understood that grammar well enough to implement it myself, not well enough to configure someone else's implementation of it.

For anyone who hasn't worked in this space: a disassembler turns machine code back into readable assembly instructions. A control-flow graph (CFG) is what you build on top of that: a graph where each node is a "basic block" (a straight run of instructions with one entry and one exit) and each edge represents a way execution can move from one block to another, whether that's falling through to the next block, taking a branch, calling a function, or returning. Once you have a CFG you can compute real software-engineering metrics on a binary you've never seen source code for: cyclomatic complexity, function boundaries, which code paths are reachable, and whether the binary is doing anything that looks like it's trying to confuse a disassembler (self-modifying jump targets, junk bytes designed to desync a naive byte-by-byte scan). That last category is called anti-disassembly detection, and it's the kind of analysis you'd actually want if you were looking at a piece of malware or a packed executable rather than a normal compiled program.

The project scope is deliberately bounded. It targets 64-bit PE executables first (Windows binaries), decodes a real but partial subset of the x86-64 instruction set (the common integer and data-movement instructions plus the SSE moves you see constantly in real compiled code), and is explicit in its own documentation about what it does not do yet: no ELF loading, no AVX/VEX encoding, no data-flow analysis, no resolving indirect branches through import tables or jump tables. The point was never to build a production disassembler. The point was to build enough of one, correctly, that the hard parts (variable-length prefix parsing, ModR/M and SIB decoding, building a real CFG with dominators, distinguishing your own code from linked-in runtime noise) actually got solved rather than skipped.

## 2. Architecture at a glance

The pipeline is a straight-line sequence of stages, and each stage lives in its own module with a narrow job. Here's what's actually in the source tree today (about 3,600 lines of Rust across `src/`), not what a planning document once said it would be:

**PE loading** (`src/pe/loader.rs`, 110 lines). Parses PE64 headers with `goblin`, but only for structure: sections, the image base, the entry point virtual address. `goblin` never touches instruction bytes. `LoadedPe` exposes a `Section` type with a `bytes_from(va)` accessor and an `is_executable()` check based on the section's `IMAGE_SCN_MEM_EXECUTE`/`IMAGE_SCN_CNT_CODE` characteristics, and that's the entire surface the rest of the pipeline needs from the container format.

**Instruction decoding** (`src/decoder/`, 1,187 lines across `mod.rs`, `modrm.rs`, `prefixes.rs`, `tables.rs`). This is the core of the project. `prefixes.rs` parses legacy prefixes and the REX byte. `modrm.rs` decodes the ModR/M byte, SIB byte, and displacement, including RIP-relative addressing (`[rip+disp]`), and renders the result as Intel-syntax operand text. `mod.rs` holds the one-byte and two-byte opcode maps and produces a `FlowKind` per instruction (`Sequential`, `CondJump{target}`, `Jump{target: Option<u64>}`, `Call{target: Option<u64>}`, `Return`, `Terminate`) that every downstream stage consumes directly instead of re-deriving control-flow behavior from the mnemonic string.

**Disassembly strategies** (`src/disassembler/`). Two independent passes over the same bytes, both always run: `linear.rs` sweeps byte-by-byte, skipping one byte and resuming on a decode failure (classic linear sweep, fooled by data embedded in code but cheap and total-coverage). `recursive.rs` follows actual control flow from a seed set (entry point plus discovered call targets) using an explicit `VecDeque` worklist and a visited set, so it never mistakes embedded data for code but can miss anything reached only through an indirect branch. Running both is what makes anti-disassembly detection possible: where the two disagree about what's an instruction is exactly where something suspicious might be happening.

**CFG construction** (`src/cfg/`). `basic_block.rs` identifies leaders (branch/call targets, the instruction after any terminator, seed addresses) and groups instructions into blocks. `graph.rs` builds a typed `petgraph` digraph with four edge kinds (`Fallthrough`, `Branch`, `Call`, `Return`) plus a single synthetic exit node that every `ret` and unresolved indirect branch converges on. `dominator.rs` implements the Cooper-Harvey-Kennedy iterative dominator algorithm.

**Function recovery** (`src/analysis/function_recovery.rs`, 174 lines). Seeds a function set from the PE entry point, every call target, and every block whose first instruction matches a recognized prologue pattern (`endbr64`, the pair `push rbp` followed by `mov rbp, rsp`, a bare `push rbp`, or a `sub rsp, imm` stack-frame allocation). Walks each seed's reachable block set using fallthrough and branch edges only, never crossing a call edge, and the first seed to reach a block owns it. Cyclomatic complexity per function comes straight from the graph: `E - N + 2`.

**Anti-disassembly detection** (`src/analysis/anti_disasm.rs`, 135 lines). Three signals computed by comparing the linear and recursive passes against each other and against the raw byte stream: jump-into-instruction (a branch target lands inside, not at the start of, an instruction the linear sweep decoded), overlapping regions (the two passes disagree about where an instruction starts), and junk-byte padding (a run of `0xCC`/`0x00`/`0x90` bytes long enough to look deliberate).

**Stats and reports** (`src/stats/`, `src/report/`). One `Stats` struct computed exactly once and handed to every reporter, so JSON, Markdown, and DOT output can never disagree with each other about a number. `report/dot.rs` emits one Graphviz digraph per recovered function with color-coded edges. `stats/accuracy.rs` implements a generic differential comparison against an `(address, mnemonic, length)` oracle stream, used both by the test suite (fed from `iced-x86`) and, later, by the `batch` command's own accuracy scoring.

**CLI** (`src/main.rs`, 280 lines, via `clap`). Two subcommands: `analyze <input> --out <dir> --mode {linear|recursive} --formats json,md,dot` for one binary, and `batch <dir> --out <dir> --mode {linear|recursive}` for a whole directory, which writes an aggregate `summary.md` and `summary.json`.

There's also an Avalonia/.NET GUI frontend (`frontend/DisasmViewer`) that came later and talks to this CLI over a process boundary rather than linking against it. I cover why in section 4 and in [ADR 0005](docs/adr/0005-frontend-process-boundary.md).

## 3. Difficulties faced, and how I solved each one

### 3.1 The anti-disassembly detector was 87% wrong on completely ordinary code

This is the difficulty I have the most concrete evidence for, because I diagnosed it byte by byte.

Running the analyzer against `bubble_sort.exe`, a 20-line sorting program from `TheAlgorithms/C` compiled with plain `-O0` and no obfuscation of any kind, produced 327 anti-disassembly flags. Not zero, not a handful. 327 flags on trivial, unmodified compiler output. That number alone was the tell that something was wrong, because nothing about that program tries to evade analysis.

I broke the 327 down by kind: 41 were `jump_into_instruction`, and 286, 87 percent of the total, were `junk_padding`. So the padding detector was the problem, and I went and looked at what it was actually flagging.

The detector's logic (`src/analysis/anti_disasm.rs`) is a raw scan over the section's byte stream, independent of the instruction stream the decoder already produced: walk the bytes, and whenever you hit a run of `0xCC`, `0x00`, or `0x90` at least `min_pad` bytes long, flag it, with a narrow carve-out that a short 0x90/0x00 run sitting exactly on a 16-byte boundary is probably just alignment. I pulled the actual bytes around a sample of the flagged offsets to see what was really there. Two things showed up immediately:

First, short runs like `5 x 0x00` and `11 x 0x90` sitting directly between two functions, right after a `ret` and right before the next function's `endbr64`. That's not obfuscation, that's the compiler padding function boundaries to a cache-line-friendly alignment, which every compiler does and every real disassembler has to know to ignore.

Second, and more interesting: some of the flagged "junk" wasn't unclaimed filler at all. At offset `0x1400014a1` I found the byte sequence `0f 1f 80 00 00 00 00`, which is a real, valid instruction: a 7-byte multi-byte NOP (`nop dword [rax+rax+0x0]`, opcode `0F 1F /0`), immediately followed by a real `movzx`-family instruction. The decoder had already successfully decoded that NOP as an instruction. The padding scanner, because it works directly on raw bytes instead of consulting the instruction stream the decoder built, had no way to know that and flagged the same bytes as suspicious filler a second time, from a completely separate code path that doesn't talk to the first one.

That's the actual lesson here, and it's a general one: a heuristic that operates on raw bytes and a heuristic that operates on a parsed instruction stream will disagree, and if you don't reconcile them you'll double-count. The detector needed to know two things it didn't have: where function boundaries actually are (which basic-block leader detection already computes), and whether the "junk" bytes it found were preceded by a real terminating instruction (`ret`, `jmp`, `ud2`) rather than floating in the middle of live code.

I want to be direct about the current status here, because it would be dishonest to claim this is fixed: it isn't. I attempted a fix that checked for a terminating opcode byte immediately preceding a padding run, got the false-positive count down from 327 to roughly 239 on a first pass, then found the fix itself was still both over- and under-inclusive (the "immediately preceding byte" heuristic doesn't correctly handle multi-byte terminators or account for the block-leader information that already exists elsewhere in the pipeline) and reverted it rather than ship something half-right. The honest state today is: the false-positive rate is fully diagnosed and documented, the root cause is understood precisely (two independent passes over the same bytes that don't share information), and the actual fix needs to route the padding scanner through the basic-block/function boundaries the CFG stage already computes instead of re-deriving terminator adjacency from scratch. That's a real, scoped next step, not a mystery.

### 3.2 Two nearly-identical 20-line programs produced wildly different numbers, and the cause wasn't in the decoder

`insertion_sort.exe` and `bubble_sort.exe`: same corpus, same tier, same compiler, same optimization level, both trivial sorting programs. Analyzing them gave:

| | insertion_sort.exe | bubble_sort.exe |
|---|---|---|
| Instructions | 312 | 1,702 |
| Basic blocks | 97 | 399 |
| Functions | 20 | 61 |
| Max cyclomatic complexity | 6 | 40 |
| Anti-disasm flags | 85 | 327 |

A 5.5x difference in instruction count between two programs that, if you read the C source, do almost the same amount of work. My first hypothesis, before I looked at anything else, was that this had to be a decoder or CFG bug. It wasn't.

I diffed the two binaries' `nm`-derived symbol tables against each other. `insertion_sort.exe` has 76 defined (`T`) symbols total. `bubble_sort.exe` has 122. The 47-symbol difference (after excluding the four genuinely different user functions, `bubbleSort`, `display`, `swap`, `test`) is entirely CRT and runtime support code, and 17 of those 47 are one specific family: `__b2d_D2A`, `__Balloc_D2A`, `__Bfree_D2A`, `__cmp_D2A`, `__d2b_D2A`, `__diff_D2A`, `__freedtoa`, `__gdtoa`, `__i2b_D2A`, `__lshift_D2A`, `__multadd_D2A`, `__mult_D2A`, `__nrv_alloc_D2A`, `__pow5mult_D2A`, `__quorem_D2A`, `__rshift_D2A`, `__rv_alloc_D2A`, `__strcp_D2A`, `__trailz_D2A`. Those are mingw's double-to-ASCII conversion routines, the arbitrary-precision decimal arithmetic that implements correctly-rounded floating-point formatting for `printf`. The rest of the diff is the wide-character and multi-byte conversion layer (`mbrtowc`, `mbsrtowcs`, `wcrtomb`, `wcslen`, `wcsnlen`, `wcsrtombs`, `MultiByteToWideChar`, `WideCharToMultiByte`, `IsDBCSLeadByteEx`) plus the printf implementation itself (`__mingw_printf`, `__mingw_pformat`) plus locale support (`localeconv`).

`bubble_sort.exe` calls `printf`. `insertion_sort.exe` doesn't. That one call statically pulls in the entire floating-point formatting engine, because mingw's `printf` has to support `%f` even if this particular call site never uses it, and the linker can't know that at link time. The 5.5x instruction-count gap and the 6.7x complexity gap have nothing to do with sorting algorithms and everything to do with which C standard library functions got linked in.

Before I did this symbol diff, I'd already chased down a different hypothesis first: that mingw's threading model (`pthread` vs `win32`) might be responsible, since that's a known source of divergent runtime behavior in mingw builds. I rebuilt the whole PE corpus after switching `update-alternatives` to the `win32` variant specifically to test that theory, and the resulting numbers came out byte-identical to the original build. That ruled it out. It's worth including here because ruling a hypothesis out with a clean rebuild is exactly as valuable as confirming one, and it's the reason I kept looking until the symbol diff actually explained the gap instead of settling for a plausible-sounding guess.

The fix wasn't a decoder change, because there was nothing wrong with the decoder. The fix was building a way to separate "your code" from "the C runtime your code happens to statically link," which is section 3.3.

### 3.3 A raw function count is a meaningless number without knowing what's actually yours

Once 3.2 made it obvious that CRT noise dominates even trivial programs, the aggregate stats the tool was reporting (89 functions, cyclomatic complexity 40, for a 20-line sort) were technically correct and practically useless. Nobody auditing `insertion_sort.c` cares that `__gdtoa`'s internal control flow has a cyclomatic complexity of 6.

I built a classifier (`src/analysis/symbol_filter.rs`, 145 lines) that cross-references each recovered function's entry address against the binary's `.symbols` file (`nm` output) and buckets it as user code or runtime/CRT, using name-pattern matching built directly from the symbol diff in 3.2 rather than a guessed list: `__mingw_*`, `__acrt_*`, `__gcc_*`, the entire `*_D2A` family, common libc names (`malloc`, `free`, `printf`, `strlen`), Win32 API names (`VirtualProtect`, `EnterCriticalSection`), and so on. The `batch` command now reports both numbers side by side: `insertion_sort.exe` becomes "8 user functions (max CC 6) / 20 total," `bubble_sort.exe` becomes "30 user functions / 61 total." That's a genuinely more honest number, and it directly reflects the ground truth the symbol file provides rather than a heuristic guess.

The lesson generalizes past this one project: any binary-analysis tool that reports aggregate metrics on a real compiled binary is reporting metrics over the runtime you happened to link, not over the code you wrote, unless it explicitly separates the two. Ground-truth symbol comparison isn't a nice-to-have for testing accuracy, it's the only way to know what your numbers actually mean.

### 3.4 The corpus itself exposed real decoder coverage gaps that curated tests never would have

The curated test table (`tests/instruction_tests.rs::CASES`, 36 hand-written cases) and the fuzz-style differential test against `iced-x86` (200,000 random 16-byte windows, of which the decoder successfully decodes 109,441, of which 106,527 are comparable against the oracle because the oracle also considers them valid, giving **100.00% length agreement** on that comparable set, verified directly rather than taken from the README) both pass cleanly and always have. Neither of them told me the decoder was missing instructions that show up constantly in real compiled code, because neither of them is drawing from real compiled code.

Running the analyzer against `lua.exe` (26,975 decoded instructions) surfaced 851 decode errors. I broke those down by opcode byte:

```
395  unsupported opcode 0x0f 0xb6   (movzx r32, r/m8)
100  unsupported opcode 0x63        (movsxd, 32->64 sign extend)
 84  unsupported opcode 0xc1        (shift group: shl/shr/sar r/m, imm8)
 72  unsupported opcode 0x98        (cwde/cdqe)
 27  unsupported opcode 0x0f 0x94   (sete)
 27  unsupported opcode 0x0f 0x95   (setne)
 26  unsupported opcode 0x0f 0xb7   (movzx r32, r/m16)
  ...
```

`movzx`, `movsxd`, and the shift group (`shl`/`shr`/`sar`) are not exotic instructions. They're some of the most common instructions in real x86-64 code, because zero/sign-extension is what happens every time a compiler moves a 32-bit array index into a 64-bit pointer computation, and shifts are everywhere in bit manipulation and multiplication-by-power-of-two optimization. `shl`/`shr`/`sar` were interesting to find specifically: they're already present in the *category classification* table (`tables.rs` lists them under `Category::Arithmetic`) but never actually implemented as opcode match arms in `mod.rs`, meaning someone had already anticipated needing them and never closed the loop.

None of this shows up if your test corpus is 36 curated snippets and 200,000 random byte windows. Random bytes are great for proving the decoder can't be made to panic or overrun its input, which is genuinely the property fuzzing is best at proving, but they're a terrible sampling distribution for "which instructions does real code actually use." The lesson: curated unit tests prove you implemented what you intended to implement correctly. Fuzzing proves you don't crash on adversarial input. Neither one proves your coverage is adequate for the actual target domain, and the only way to find that out is to run the tool against a large, real, diverse corpus and look at what it couldn't decode.

The same corpus run also quantified a documented-but-unmeasured scope gap precisely: `lua.exe` has 78 indirect jumps and 60 indirect calls, all 138 unresolved (0 resolved), because the decoder correctly identifies `jmp [rip+x]`-style targets as indirect but the analysis layer doesn't chase them through the binary's data sections. That's explicitly out of scope per [ADR 0003](docs/adr/0003-pe-first.md) (no IAT parsing yet), but "0 out of 138 resolved" is a much more honest way to say that than a scope note in a README.

### 3.5 A stable-labeled dependency crashed on startup, and the fix was pinning to a dev build

This one is entirely a frontend/tooling difficulty, not a decoder difficulty, but it cost real debugging time and the failure mode is instructive on its own.

I added `LiveChartsCore.SkiaSharpView.Avalonia` version 2.0.5, the latest non-prerelease release on NuGet, to render the stats dashboard. The app built cleanly with zero warnings. On first launch it crashed immediately:

```
System.MissingFieldException: Field not found: 'Avalonia.Input.Gestures.PinchEvent'.
   at LiveChartsGeneratedCode.SourceGenCartesianChart..ctor()
```

That's a binary compatibility failure, not a compile-time one: the LiveCharts package had been built against an older Avalonia release and referenced a static field that no longer exists in Avalonia 12.1.1, the version this project's frontend actually uses. Nothing about the type signatures changed enough to fail at compile time, because the field lookup only gets resolved at runtime via reflection inside LiveCharts' own source-generated chart constructor. The build succeeding told me nothing useful.

I checked the LiveCharts NuGet dependency manifest for a version that explicitly declared compatibility with Avalonia 12: `2.1.0-dev-798`'s `.nuspec` lists `Avalonia >= 12.0.0` as a dependency, versus 2.0.5's older constraint. Pinning to that dev build fixed the crash immediately. The lesson: a package's "stable" version number tells you about its own API stability, not about which version of its own dependencies it was actually built and tested against. When you hit a runtime `MissingFieldException` or `MissingMethodException` against a library that compiled fine, check the actual dependency manifest of the version you're using, not just its semver label.

### 3.6 Avalonia's compiled-bindings field generator silently skips anything that isn't in the visual tree

While building pan/zoom for the CFG viewer, I wrote XAML that named a `ScaleTransform` and a `TranslateTransform` inside an `<Image.RenderTransform>` block with `x:Name`, expecting the code-behind to get generated fields for them the way it does for every named `Control`. The compile failed with:

```
error CS0103: The name 'ScalePart' does not exist in the current context
```

repeated for every reference to it. The XAML itself compiled without a XAML-specific error (no `AVLN2000`), which was the confusing part: if the name were unresolvable at the XAML level I'd have gotten a XAML compiler error pointing at the exact line. Instead the field just silently never got generated, and the failure only showed up as an ordinary C# "name doesn't exist" at every use site in the code-behind.

The actual cause: Avalonia's compiled-bindings field generator walks the visual/logical tree to find named elements, and `Transform` objects (`ScaleTransform`, `TranslateTransform`, `TransformGroup`) aren't part of that tree. They're property values, not children. `x:Name` on a `Control` works because `Control`s are tree nodes. `x:Name` on a `Transform` is syntactically legal XAML and silently produces nothing, because the generator never visits it. The fix was to stop trying to name the transforms in markup at all and instead build them directly in code-behind (`new ScaleTransform()`, `new TranslateTransform()`, wrap them in a `TransformGroup`, assign that to `Image.RenderTransform` in the constructor after `InitializeComponent()`), which sidesteps the field-generation path entirely. The general lesson: a markup language's naming/binding conventions don't automatically extend to every object graph you can construct in it. If a framework generates code from your markup, that generation has its own model of what counts as "in the tree," and it's worth checking that model rather than assuming a pattern that works for one node type works for a related one.

### 3.7 The backend's own accuracy numbers never reached the machine-readable output they were computed for

While wiring the accuracy report into the `batch` command's output, I found that `AnalysisResult.accuracy` (an `Option<AccuracyReport>`, meant to carry the `iced-x86` differential comparison result) is always `None` in the actual JSON the tool emits. The type exists, the comparison logic exists and gets run, but `pipeline::analyze` always passes `None` into `report::build` regardless. And separately, the `batch` subcommand does compute per-binary mnemonic/length match percentages, but only ever formats them directly into the `summary.md` Markdown string in `main.rs`. Neither path attaches the number back onto the object that becomes an entry in `summary.json`.

The practical effect: a program consuming the tool's JSON output has no way to see accuracy numbers at all, even though a human reading the Markdown report can see them right there in the table. I hit this directly while building the GUI's batch/report browser screen, which needed exactly that number, and had to work around it by parsing the Markdown table with a regex rather than reading the JSON, which I flagged clearly in the frontend's own schema documentation (`frontend/analysis_result.schema.json`) as a backend-side gap rather than quietly working around it and saying nothing. This is a common and easy mistake: computing a value once for a human-facing report and never wiring the same value into the machine-facing one, so the two outputs silently drift out of parity with each other. The fix, when it happens, is small (attach the already-computed `AccuracyReport` onto the result before serializing), but the fact that it slipped through despite the value being computed correctly and used correctly in one output format is worth remembering.

### 3.8 Making "install once, get both a CLI and a GUI" actually true, not just documented

After building the GUI, I wanted a user to be able to get either a scriptable CLI or a visual app from one download, without a separate install step or environment variable to configure. The GUI already spawned the CLI as a subprocess and searched for it in a few places (an explicit configured path, a `DISASM_CFG_BIN` environment variable, walking up from the app's own directory looking for a dev-checkout's `target/release/`, and finally a plain `PATH` lookup), but none of those checks covered the actual layout a packaged release would use: the CLI binary sitting in the exact same folder as the GUI executable.

I wrote that assumption into a packaging script and a README section before checking whether the discovery logic actually supported it, which would have shipped a false claim. Reading `BackendLocator.Find` confirmed the gap directly: it never checked `AppContext.BaseDirectory` for a sibling binary, only for a `target/release` subdirectory several levels up. I added that sibling check as the highest-priority automatic lookup (after an explicit path or env var override, before the dev-checkout walk), then verified it for real rather than trusting the fix: built the CLI natively for Linux and cross-compiled it for Windows (`cargo build --release --target x86_64-pc-windows-gnu`, which worked immediately using the same `mingw-w64` toolchain already used to build the PE test corpus), published the GUI for both RIDs with `dotnet publish`, dropped both binaries into one folder per platform with a script, ran the bundled CLI directly to confirm pure command-line use still worked, and then launched the bundled GUI with `PATH` deliberately restricted to `/usr/bin:/bin` and `DISASM_CFG_BIN` explicitly unset, the conditions under which the claim would fail if it were false. It launched and rendered cleanly. That's the difference between a plausible-sounding packaging claim and a verified one.

## 4. What I'd tell someone attempting something similar

**Build the test oracle before you trust a single decoded instruction.** The differential harness against `iced-x86` is a dev-only dependency, never linked into the actual decode path (see [ADR 0002](docs/adr/0002-iced-x86-as-oracle.md)), and it's what let me say "100.00% length agreement across 106,527 comparable random-byte instructions" with a straight face instead of just asserting it. Writing your own decoder without a second, independent implementation to check against means you have no way to know if you're wrong, because a hand-written decoder that agrees with your own mental model of the spec will look correct to you specifically.

**Fuzzing tells you a narrower thing than you think it does.** It's excellent, close to indispensable, for proving your decoder can't be driven into a panic or an out-of-bounds read on adversarial or malformed input, which matters a lot if this tool is ever going to touch untrusted binaries. It tells you almost nothing about whether your instruction coverage matches what real compiled code actually contains, because random bytes and real compiler output have wildly different statistical distributions. You need both a fuzz corpus and a real-world corpus, and they're testing different properties.

**Run against real, diverse, compiler-generated binaries as early as possible, not after the decoder feels done.** Section 3.4's coverage gaps (`movzx`, `movsxd`, the entire shift group missing) would have been trivial to find and fix early, and instead sat undiscovered through a complete, cleanly-passing curated test suite because the curated tests were written by the same person who wrote the decoder, testing the cases they already knew to test. A real corpus, even a small one, surfaces the instructions you didn't think to write a test for, because it wasn't built with your test coverage in mind.

**Ground-truth symbol comparison is not optional if you're going to report any aggregate metric on a real binary.** Section 3.2 and 3.3 together are really one lesson: raw instruction counts, function counts, and complexity scores on a linked binary are dominated by whatever runtime got statically pulled in, and you cannot tell that from the numbers alone. If your tool reports metrics without a way to separate "code the target project wrote" from "code the compiler's runtime brought along," those metrics will be misleading on every single non-trivial binary you point it at, not occasionally.

**Third-party crates are fine for infrastructure, corrosive for the thing you're claiming to have built.** `goblin` for PE header parsing and `petgraph` for the graph container are both completely reasonable: neither one does the decoding work that's the actual point of the project. `iced-x86` staying a dev-only oracle dependency, never imported from `src/decoder/`, is the boundary that keeps the whole project honest about what it is. If I'd pulled in an existing disassembler for the actual decode path, the entire project would be a wrapper with extra steps, and the ModR/M/SIB/REX work that's genuinely the hard and interesting part would never have happened. Decide up front which dependencies are load-bearing infrastructure and which ones would quietly replace the point of the exercise, and hold that line even when the load-bearing ones are annoying to configure.

**Don't trust a package's semver label to mean its runtime dependencies match yours.** Section 3.5's `MissingFieldException` came from a "stable" NuGet package built against an older transitive dependency than the one actually in the project. When something built cleanly crashes at runtime with a missing-member exception against a library, that's almost always a binary compatibility mismatch, not a bug in your code, and the fix is checking what version of its own dependencies the library you're pinned to actually declares.

**If you make a packaging or architecture claim in a README, verify it under the conditions where it would fail, not the conditions where it's convenient to test.** Section 3.8's "no PATH setup needed" claim would have been false if I'd only tested it in a dev shell where the CLI happened to already be reachable through the existing `target/release` walk-up logic. Testing it with `PATH` deliberately restricted and the fallback environment variable deliberately unset is what actually proves the claim rather than just asserting it.

**The most surprising thing, in hindsight, wasn't a decoder bug at all.** It was how completely CRT and runtime linkage dominates the analysis of even the smallest, simplest programs. A 20-line insertion sort and a 20-line bubble sort produced numbers 5 to 6 times apart from each other, and the entire gap traced to one `printf` call statically pulling in an arbitrary-precision decimal arithmetic library for floating-point formatting that the program never actually exercises. If you're building anything that reports metrics on compiled binaries, budget real time for separating your target's code from its linked runtime, because that separation isn't a polish feature, it's the difference between your tool's numbers meaning anything at all.

## 5. Current state and honest limitations

**What's actually working, verified directly rather than assumed:**

- PE64 loading, sections, entry point, executable-section detection.
- A real hand-written decoder covering legacy/REX prefixes, ModR/M, SIB, RIP-relative addressing, and a genuine (if partial) opcode subset: the standard ALU grid, `mov`/`lea` in their common forms, `push`/`pop`, `call`/`jmp`/`jcc`, `test`/`cmp`, common SSE moves, and the terminators (`ret`, `int3`, `hlt`, `ud2`, `nop`, `endbr64`).
- Linear sweep and recursive descent, both always run, feeding a comparison that powers anti-disassembly detection.
- A real CFG with typed edges and a `petgraph` backing, function recovery via prologue heuristics and call-target aggregation, cyclomatic complexity computed correctly from the graph.
- 100.00% instruction-length agreement against `iced-x86` on the comparable subset of 200,000 random-byte trials, and all 36 curated table-test cases passing exactly.
- JSON, Markdown, and DOT reporting, plus a batch mode that aggregates a whole directory and now separates user code from CRT/runtime code by cross-referencing symbol files.
- A GUI frontend (Avalonia/.NET, 2,321 lines of C# plus about 500 lines of XAML) that talks to the CLI over a process boundary, with 33 passing tests of its own covering the JSON parsing, process-invocation error handling, and ViewModel filter/sort logic.

**What's built but not actually connected to anything:** the dominator computation in `src/cfg/dominator.rs` (125 lines, implementing Cooper-Harvey-Kennedy correctly by inspection) is never called from `pipeline.rs`, never wired into any report, and has no dedicated test. It exists as a standalone, publicly-exported module that nothing in the running tool currently uses. If natural-loop detection or a dominator-tree view is ever wanted, the algorithm is already there and just needs a caller.

**What's diagnosed but not fixed:** the anti-disassembly junk-padding detector's 87% false-positive rate on ordinary compiler output (section 3.1). The root cause is fully understood and documented. The actual fix needs to route the raw byte-level padding scanner through the basic-block/function-boundary information the CFG stage already has, and I chose not to ship a partial fix rather than leave a half-corrected detector in place.

**What's a known, explicit scope boundary, not a bug:** ELF loading (PE-only for now, per [ADR 0003](docs/adr/0003-pe-first.md), even though the local test corpus includes ELF builds of every sample for future use). AVX/VEX/EVEX encodings. Data-flow or def-use analysis. Indirect-branch resolution: on `lua.exe`, a real, moderately complex binary, 138 indirect calls and jumps were found and precisely zero were resolved, which is the honest, measured version of "the tool doesn't chase function pointers or jump tables yet."

**What's a measured coverage gap, not yet closed:** the decoder currently fails to decode `movzx`, `movsxd`, and the entire shift-group family (`shl`/`shr`/`sar`) among others, which are common enough in real compiled code that `lua.exe` alone produced 851 decode errors, with those specific opcodes accounting for the large majority of them. `shl`/`shr`/`sar` are already anticipated in the category-classification table, just never implemented as opcode match arms, so closing this gap is a scoped, well-understood piece of work rather than an open question.

**Backend/frontend JSON contract gap:** the accuracy report (`mnemonic_match_pct`, `length_match_pct`) that `batch` computes per binary is real and correct, but never gets attached to the JSON output, only to the Markdown table (section 3.7). The frontend works around this today by parsing the Markdown table directly rather than duplicating the accuracy computation client-side, which is documented as a known gap in `frontend/analysis_result.schema.json` rather than silently patched over.
